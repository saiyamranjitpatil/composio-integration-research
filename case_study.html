01 · Executive summary

The integration surface is standardized in some places and surprisingly fragmented in others.

Authentication has strong recurring patterns, but access requirements, MCP support, and practical buildability are much less uniform. The research therefore needs to separate “an API exists” from “an integration can actually be built today.”

03 · Agent workflow

Evidence first, synthesis second, verification last.

The system deliberately separates retrieval from reasoning. The language model receives collected evidence rather than being asked to invent facts from its prior knowledge.

01

App inventory

Load the fixed 100-app assignment dataset.

02

Evidence search

Search targeted API, authentication, pricing and MCP queries.

03

Evidence store

Preserve source titles, URLs and extracted evidence text.

04

Qwen synthesis

Convert evidence into a constrained structured record.

05

Normalization

Collapse equivalent authentication labels into a usable taxonomy.

06

Human verification

Check a risk-prioritized sample against documentation.

Evidence layer
raw_evidence.json stores the evidence gathered for all 100 apps. The final run produced 527 source records.
Research layer
results.json contains the structured LLM synthesis for the application inventory.
Quality layer
normalize.py, verify.py, and finalize.py separate normalization, verification, and final reconciliation from the research engine.
Analysis layer
final_analysis.py calculates portfolio-level patterns from the corrected final dataset.
04 · Verification

The verification sample is the proof that the pipeline needs a quality loop.

Ten high-risk records were checked against documentation. The sample produced 50 field-level judgments. 32 were correct on the first pass, while 18 required correction.

64%

First-pass field-level accuracy across the 10-app verification sample.

Apps verified 10
Field checks 50
Correct first-pass fields 32
Field corrections 18
Apps requiring correction 9 / 10

What went wrong?

The recurring failure modes were over-conservative access classification, incomplete authentication extraction, and missed official MCP implementations.

What changed?

Verified corrections were applied downstream to produce final_results.json without overwriting the original research output.

Why keep the errors?

The original output remains auditable. The system does not silently rewrite history; it preserves the research, verification, and corrected layers separately.

07 · Reproducibility

The research can be inspected and rerun from the repository.

The pipeline is intentionally decomposed into explicit stages. The commands below describe the major execution path.

python Agent/bulk_research.py Collect evidence for 100 apps
python Agent/synthesize.py --limit 5 Synthesize evidence with Qwen
python Agent/normalize.py Normalize authentication taxonomy
python Agent/verify.py Generate verification queue
python Agent/apply_verification.py Record verified sample corrections
python Agent/finalize.py Create corrected final dataset
python Agent/final_analysis.py Generate portfolio-level findings

Important limitation

The 64% figure is a first-pass field-level accuracy result for the 10-app verification sample. It should not be presented as an estimated accuracy rate for all 100 apps. The remaining 90 records retain their evidence and confidence metadata but were not manually verified in this exercise.
